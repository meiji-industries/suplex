# Domain documentation

For product claims, requirements discovery, or marketing research, start with
[the product guide](../product.md). It separates implemented support from limits
and unverified claims. Read [CONTEXT.md](../../CONTEXT.md) for domain terms.

Follow the guide's source links and inspect current routes, configuration,
behavior, and tests before asserting availability. A test fixture establishes
only the behavior it exercises; it does not verify a live account or release.

Read [the current architecture](../architecture/README.md) for runtime ownership and
behavior, including Herdr. Read relevant [ADRs](../adr/) when an engineering decision needs explanation.
Their dated probes and original implementation details are historical context.
When current code differs, describe the discrepancy and correct the stale
reference rather than importing an old requirement into new work.

Completed plans, superseded designs, and old reviews are available in Git
history. Retained proposals must identify their unimplemented scope. Neither
proposals nor old acceptance checklists establish current product requirements.
